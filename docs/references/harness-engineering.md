# Reference: 工程技术——在智能体优先的世界中利用 Codex（Harness Engineering）

> 状态：reference（原文存档，只读不改） · 归档：2026-06-27
> 来源：OpenAI 博客，2026-02-11，作者 Ryan Lopopolo。
> **本项目对它的提炼与采纳见 [`docs/design-docs/core-beliefs.md`](../design-docs/core-beliefs.md)**（单一真相来源；此处仅存原文供追溯）。

---

在过去五个月里，团队进行了一项实验：构建并交付一款软件产品的内部 beta 版，**其中没有一行代码是人工编写的**。每一行代码——从应用逻辑、测试、CI 配置、文档、可观察性到内部工具——全部由 Codex 编写，估计只用了手工编码约 1/10 的时间。

**人类掌舵。智能体执行。**

当软件工程团队的主要工作不再是编写代码，而是**设计环境、明确意图、构建反馈回路**，使 Codex 能可靠工作时，会发生哪些变化——这是本文要讲的经验教训：哪里出错、问题如何叠加、如何最大化利用唯一真正稀缺的资源：**人类的时间和注意力**。

## 我们从一个空的 Git 代码仓库开始

首次提交到空仓库是在 2025 年 8 月下旬。初始架构（仓库结构、CI、格式化规则、包管理、应用框架）由 Codex CLI 用 GPT‑5 在一小套模板指导下生成，连初始 `AGENTS.md` 都是 Codex 写的。系统没有预存任何人工代码——从一开始仓库就由智能体塑造。

五个月后，仓库约一百万行代码。约 1,500 个 PR 被打开与合并，背后只有三名工程师（后扩到七名，吞吐量反而**增加**）。平均每位工程师每天 3.5 个 PR。这不是为输出而输出：产品已在数百名内测用户处投入使用。人类从未直接贡献代码——这成为核心理念：**不手动编写代码**。

## 重新定义工程师的角色

由于不写代码，**工程师的重点转向系统、架构和杠杆作用**。

早期进展慢，不是因为 Codex 没能力，而是**环境规范不够明确**：智能体缺少实现高级目标所需的工具、抽象层和内部结构。工程团队的主要任务变成了「协助智能体完成有用的工作」。

实践上是深度优先：把大目标拆成更小的构建模块（设计、代码、评审、测试），提示智能体去构建，再用它们解锁更复杂的任务。事情不顺时，解法几乎从来不是「再努力一点」，而是追问：**「究竟还需要什么能力？我们又该如何让它对智能体既清晰可读又可强制执行？」**

人类几乎完全通过提示交互：描述任务、运行智能体、允许其开 PR，并指示 Codex 本地自审、请求额外的智能体评审、响应反馈、循环往复直到所有评审者满意（一个 Ralph Wiggum 循环）。Codex 直接使用标准开发工具（gh、本地脚本、嵌入仓库的技能）收集情境，无需人工复制粘贴。

## 提高应用程序的可读性

吞吐量上升后，瓶颈变成人工 QA。由于人类时间固定，团队努力让 UI、日志、应用指标**对 Codex 直接可读**：

- 应用可按 git worktree 启动，Codex 为每次更改启动并驱动一个实例。
- 接入 Chrome DevTools 协议，创建处理 DOM 快照、截图、导航的技能——Codex 能复现错误、验证修复、推理 UI 行为。
- 可观测性同理：日志/指标/追踪经本地临时栈展示给 Codex（任务完成即删）。智能体用 LogQL 查日志、PromQL 查指标。于是「确保服务在 800ms 内启动」「这四个关键旅程的任何 span 不超过两秒」这类提示变得可行。

> 常见到单次 Codex 运行在一个任务上持续工作超过六小时（通常在人类睡眠时间）。

## 我们将代码仓库设为记录系统

情境管理是让智能体在大型复杂任务中有效发挥的最大挑战之一。最早的教训很简单：**要给 Codex 的是一张地图，而不是一本 1,000 页的说明书。**

「一个大型 AGENTS.md」的尝试失败了：

1. **情境是稀缺资源。** 巨大的指令文件会挤掉任务、代码和相关文档——智能体要么错过关键约束，要么针对错误约束优化。
2. **过多指导反而无效。** 当一切都「重要」时，一切都不重要了；智能体最终在本地模式匹配，而非有意识地导航。
3. **它会立即腐烂。** 庞杂手册变成陈旧规则的坟场；人类一旦停止维护，它就成了有吸引力的麻烦源头。
4. **很难核实。** 单个 blob 不适合机械检查（覆盖率、新鲜度、所有权、交叉链接），漂移不可避免。

因此不再把 AGENTS.md 当百科全书，而是当**内容目录**。知识库放在结构化的 `docs/` 目录（作为记录系统）；一份简短的 `AGENTS.md`（约 100 行）注入情境，作地图，指向更深层的真实来源：

```
AGENTS.md
ARCHITECTURE.md
docs/
├── design-docs/
│   ├── index.md
│   ├── core-beliefs.md
│   └── ...
├── exec-plans/
│   ├── active/
│   ├── completed/
│   └── tech-debt-tracker.md
├── generated/
│   └── db-schema.md
├── product-specs/
│   ├── index.md
│   ├── new-user-onboarding.md
│   └── ...
├── references/
│   ├── design-system-reference-llms.txt
│   ├── nixpacks-llms.txt
│   ├── uv-llms.txt
│   └── ...
├── DESIGN.md
├── FRONTEND.md
├── PLANS.md
├── PRODUCT_SENSE.md
├── QUALITY_SCORE.md
├── RELIABILITY.md
└── SECURITY.md
```

- 设计文档被编目索引，含验证状态与一套定义「智能体优先操作原则」的核心理念。
- 架构文档提供域与包分层的顶层地图；质量文档对每个产品领域和架构层评分，追踪差距。
- **计划是一等工件**：小改用临时轻量计划，复杂工作进执行计划，附进度与决策日志，提交入库。活跃/已完成/技术债都版本化集中存放，使智能体不依赖外部情境即可运行。

这实现**渐进式披露**：从一个小而稳定的切入点开始，被指引「下一步看哪里」，而非一上来被淹没。专职 linter 和 CI 验证知识库新鲜度、交叉链接与结构；定期运行的「doc-gardening」智能体扫描过时/废弃文档并发起修复 PR。

## 目标是智能体的可读性

仓库完全由智能体生成，所以首先针对 **Codex 的可读性**优化。像帮新人快速上手一样组织仓库，让智能体能**直接从仓库**推理出完整业务域。

> 从智能体角度，**运行时进不了情境的东西 = 不存在**。Google Docs、聊天记录、人脑里的知识系统都访问不到。只有仓库本地、已版本化的工件（代码、Markdown、schema、可执行计划）才算数。

那次让团队在架构模式上达成一致的 Slack 讨论？智能体若发现不了，就像迟到三个月的新员工一样一无所知。所以要不断把更多情境推进仓库——组织并展示正确信息供推理，而非用临时指令把它压垮。像给新队友引导产品原则、工程规范、团队文化一样把这些喂给智能体，会带来更一致的输出。

这一框架带来取舍：倾向选择能完全内化于「在仓库中推理」的依赖与抽象。所谓「枯燥」的技术因其可组合性、API 稳定性、训练集表现而更易建模。有时让智能体重写部分子集，比绕过公共库不透明的上游行为更便宜——例如不引入通用 `p-limit`，而是自己实现带并发的 map 辅助函数：与 OpenTelemetry 紧密集成、100% 测试覆盖、行为完全符合运行时预期。

把系统更多部分变成智能体可检查、可验证、可直接修改的形式，直接提高杠杆——不只对 Codex，对其他智能体（如 Aardvark）亦然。

## 规范架构与品味

仅靠文档无法保持全智能体生成代码库的连贯。**通过强制不变量、而非微观管理实现过程**，让智能体快速交付又不削弱基础。例如要求 Codex 在边界处解析数据形状，但不规定实现方式（模型偏好 Zod，但未指定库）。

智能体在**严格边界 + 可预测结构**中最高效，因此围绕严格架构模型构建应用：每个业务域划分为固定的层，依赖方向被严格验证，只允许有限的边。约束由自定义 linter（同样由 Codex 生成）和结构测试机械强制。

规则示意：每个业务域内，代码只能「向前」依赖固定的层（**Types → Config → Repo → Service → Runtime → UI**）；横切关注点（认证、连接器、遥测、功能标志）通过单一显式接口 **Providers** 进入；其他一律不允许，并自动强制。

这种架构通常要到数百名工程师才会推行；对编码智能体而言是**早期先决条件**：有约束，速度才不掉、架构才不漂移。还辅以一小组「品味不变式」（结构化日志、命名约定、文件大小限制、平台可靠性要求）。因为 lint 是自定义的，错误信息里会**注入修复指令**到智能体情境。

在以人为本的流程里这些规则可能显得迂腐；有了智能体，它们成了倍增器——一旦编码，立即应用于所有地方。同时明确**哪里需要约束、哪里不需要**：中央强制边界、本地允许自主。生成的代码不总符合人类风格偏好也没关系——只要正确、可维护、对未来智能体运行清晰可读即达标。人类品味持续反馈进系统：评审意见、重构 PR、用户 Bug 被记成文档更新或直接编码进工具；**文档不够时，就把规则变成代码**。

## 吞吐量改变了合并的理念

随 Codex 吞吐量上升，许多传统工程规范失效。仓库运行中尽量减少阻塞合并门，PR 生命周期很短；偶发测试失败通常靠重跑解决，而非无限期阻塞。在智能体吞吐量远超人类注意力的系统中，**纠错成本低，等待成本高**。在低吞吐环境这样做不负责任，在这里通常是正确选择。

## 「智能体生成」实际上意味着什么

指的是整个代码库。智能体的产出包括：产品代码与测试、CI 配置与发布工具、内部开发者工具、文档与设计历史、评估框架、评审意见与回复、管理仓库自身的脚本、生产仪表板定义。

人类始终参与，但抽象层次不同：优先排序工作、把用户反馈转成验收标准、验证结果。智能体遇困时被视为信号——识别缺失的工具/指导/约束/文档并反馈进仓库，且**始终由 Codex 自己写修复**。智能体直接用标准开发工具：拉评审反馈、行内回复、推更新，常自行 squash 合并自己的 PR。

## 不断提高的自主水平

随着测试、验证、评审、反馈处理、恢复被直接编码进系统，仓库最近跨过一道门槛：Codex 能端到端驱动一个新功能。给定一个提示，智能体现在可以：验证仓库当前状态 → 复现报告的 bug → 录制故障演示视频 → 实施修复 → 运行应用验证修复 → 录制解决方案视频 → 开 PR → 响应智能体与人类反馈 → 检测并修复构建故障 → 仅在需要判断时交人工 → 合并。

> 此行为高度依赖该仓库的具体结构与工具，不应假定在没有类似投入下可泛化——至少目前不行。

## 熵与垃圾收集

完全自主也带来新问题：Codex 会复现仓库中已有的模式——包括不理想的，随时间不可避免地漂移。最初人类手动处理（每周五花 20% 时间清「AI 残渣」），不可扩展。

于是把「黄金原则」直接编码进仓库，并建立循环清理：这些是带主观意见的机械规则，保持可读性与一致性。例如 (1) 偏好共享实用包而非手写辅助，以集中管理不变量；(2) 不做「YOLO 式」探测数据——验证边界或依赖类型化 SDK，避免基于猜测的结构构建。定期跑一组后台 Codex 任务扫描偏差、更新质量等级、发起定向重构 PR，大多一分钟内可审完自动合并。

> 其功能类似垃圾回收。技术债像高息贷款：持续小额偿还，远好过累积后痛苦一次清。人类品味一旦被捕捉，就持续应用于每一行代码。

## 我们仍在学习的内容

策略在 OpenAI 内部发布中表现良好。为真实用户造真实产品，把投资锚定现实、引向长期可维护性。

尚不清楚的是：完全智能体生成的系统里架构连贯性如何随时间演变；人类判断力在哪里最有用、如何编码使其放大;模型变强后系统如何演变。

显而易见的是：**构建软件仍需纪律，但纪律更多体现在支撑结构上，而非代码上**。保持一致性的工具、抽象和反馈回路愈发重要。当前最棘手的挑战集中在**设计环境、反馈回路和控制系统**——帮智能体大规模构建并维护复杂可靠的软件。
