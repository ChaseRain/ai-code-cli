# Core Beliefs — 操作原则（Agent 优先 / Harness 工程）

> 状态：active · 最后更新：2026-06-27
> 这是本项目的「宪法」。所有 spec、计划、代码冲突时以此为准。

## A. 代码仓库即记录系统（System of Record）

1. **运行时进不了上下文的知识 = 不存在。** Google Docs、聊天记录、人脑里的约定，对 Agent 都不可见。
   只有仓库本地、已版本化的工件（代码、Markdown、schema、可执行计划）才算数。
2. **为 Agent 可读性优化。** 像帮新人快速上手一样组织仓库——让 Agent 能直接从仓库推理出完整业务域。
3. **地图，不是手册。** `AGENTS.md`（≈100 行）是目录与指针；真相分布在结构化的 `docs/`。
4. **渐进式披露。** 从小而稳的入口出发，被指引「下一步看哪里」，而不是一开始吞下千页说明书。
5. **计划是一等工件。** 小改用轻量临时计划；复杂工作进 `docs/exec-plans/`，带进度与决策日志，提交入库。
6. **文档会腐烂——所以可核验。** 每篇带状态/最后更新；交叉链接、单一真相来源；过时即标记或删，宁缺毋滥。

## B. Harness 工程五准则

> Harness = 模型之外的一切：循环、工具、上下文、解析、错误处理、可观测性。
> 模型负责**决策**，harness 负责**执行与守护栏**。

1. **循环极简且可观测。** Agent Loop 是一条清晰的 `决策→工具→结果→再决策`，每步可日志、TUI 可见。
2. **工具少而精，schema 清晰。** 首期只 7 个原子工具，输入/输出/错误结构统一；宁可少不可重叠。
3. **上下文刻意管理。** 进入 context 的内容（系统提示、历史、工具结果、权限拒绝、错误）都是显式决定的。
   *上下文是稀缺资源*：一份巨大的指令文件会挤掉任务、代码与相关文档——本项目据此拒绝单体 spec。
4. **错误即数据。** 工具错误、权限拒绝、超时都转成结构化结果回喂模型，让它自行恢复，而非崩溃。
5. **模型决策 / harness 守护。** 权限确认、最大轮次、超时、重试、路径沙箱由 harness 强制，不靠模型自觉。

## C. 首期纪律

- **less is more 是第一原则。** 唯一目标：稳定跑通基线 + 测试齐全。
- 扩展能力（上下文压缩、多 Provider、resume）**不替代、不弱化**基础功能；登记在 `tech-debt-tracker.md`。
