# 代码评审

当用户要求「review 一下 / 代码评审 / 看看这段代码有没有问题」时，按下面维度做一次结构化评审。

## 收集上下文

1. 若评审目标是工作区改动，用 `run_shell` 跑 `git diff`（或 `git diff --staged`）拿到 diff。
2. 若指定了文件/目录，用 `read_file` / `grep` 读取相关实现与其调用方，理解上下文再评审。

## 评审维度

- **正确性**：边界条件、空值/错误处理、并发与竞态、资源释放。
- **安全**：注入、路径穿越、敏感信息泄露、权限边界。
- **可维护性**：命名、职责单一、重复代码、过度抽象。
- **测试**：关键路径是否有测试覆盖；改动是否破坏既有行为。
- **一致性**：是否遵循项目既有风格与约定（不要引入与本项目无关的范式）。

## 输出格式

按严重度分级列出问题，每条给出「位置 + 问题 + 建议」：

- 🔴 必须修复（会导致 bug / 安全问题）
- 🟡 建议改进（可维护性 / 健壮性）
- 🟢 可选优化（风格 / 细节）

最后给一句总体结论（可合并 / 需修改后再合并）。

## 约束

- 只评审、不擅自改代码；如需改动，先说明再征得用户同意。
- 评论对事不对人，给出具体可执行的建议而非空泛批评。
